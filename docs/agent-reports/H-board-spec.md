# Agent H — ホワイトボードモード仕様「ぶどう棚」(2026-08-21)

要望: ホワイトボード形式のロードマップ。マットな円、押すとブドウのようにサブ要素が展開。

## マッピングの裁定: 円=マイルストーン、実=タスク

大円=達成すべき状態(エビデンス)、押すと貢献タスクが実として展開。
- ロードマップとして真(タスクの地図はTodoグラフでプロダクト命題に反する)
- スキーマ追加は `milestones.board_x/board_y` の2列のみ(サブタスク新設はしない)
- 「円を押す→中身がブドウ状に開く」体験は完全に満たされる
- Objective=左上固定オーバーレイ(タイトル+残りN日+≈%)
- Workstream=新色相は導入しない(色=切迫度の一本規則)。初期配置の行+クラスタ重心
  チップ「ユーザー需要 ◉Soya」で示す
- 未分類タスクは盤に置かず右下トレイ「未分類 N件」(リンク)

## ノード解剖

**マイルストーン円(マット)**: 直径 56〜96px `d=56+40×(weight/maxWeight)`。塗り=フラット
#131b2b(グロー無し)。縁1.5px=期限の切迫ランプ。円周に進捗アーク(4px白85%/トラック白8%)。
中央にモノ体フラクション15px/700+単位10px。タイトルは円の下12px 2行clamp。
達成=緑マットで後退(.75)。除外=非表示。期限超過=縁critical、**脈動は最も超過が古い1円だけ**。
収納時は右下に「⠿ N」(未完了実数、無彩)。

**実(ベリー)**: 22px、マット#1a2334+縁白15%。完了=#173327+✓で減光35%。p0/切迫=縁ランプ色。
ブロック=⚑。実は**親ノード内部の子要素**(rotate/translate配置 — Tastroの衛星方式、
ドラッグ追従と衝突管理が自動で解決)。房は下向き扇200°→340°、r1=d/2+30(6粒)、r2=r1+32
(7〜12粒)、13粒以上は「+N」。茎=1px白20%。bloom: scale0→1+径方向、
cubic-bezier(.2,.9,.3,1.2) 220ms、30msスタガー。収納160ms逆再生。展開状態はlocalStorage。

## 盤のメカニクス

- 永続化: `milestones.board_x/board_y REAL nullable`。dragstopでserver action。
  盤座標は会社状態ではない→activity_logに記録しない。カメラはlocalStorage。
- 初期自動配置(board_x=nullのみ): 列=**いま(≤14日)/次(≤45日)/その先**(Now-Next-Later —
  検証期に日付固定タイムラインは偽の確実性)、行=workstream。ドラッグした円だけ座標固定、
  未ドラッグはレイアウト追従(Tastroの共存パターン)。「整列」=全座標null化。
- 盤上作成: 空白ダブルクリック→マイルストーン作成(MILESTONE_RULEヒント付き)。
  房末尾の「+」実→タスク名だけでインライン追加。
- クイック操作: 円中央フラクション→カウンターポップオーバー(5秒入力維持)。
  実クリック→ミニポップオーバー(✓完了/期限/担当/開く)。`u`は全画面共通。

## 可読性の保証(「今週何をやるか」3秒)

①左端の列=いま — 空間が答える ②縁ランプで熱い円が目立つ、超過は1つだけ脈動
③達成円・完了実は減光 — 残作業だけ明るい ④左上オーバーレイが目標と残り日数を常掲
⑤p0/超過の実にランプドット ⑥データはダッシュボードと同一サービス層。

## 技術裁定

**@xyflow/react 12.11.3 で確定**(Tastroが同パッケージをReact 19で実証済み)。
Tastroから移植するパターン: `nodeOrigin=[0.5,0.5]` / ドラッグ中のノード再構築を

三大落とし穴: ①revalidate起因のドラッグ中ノード再構築 ②nodeOrigin後変更で座標全ずれ
③style.cssのimport忘れ。

# 追補 II — 期間ナビゲーションと「白い作業台」(2026-08-21)

ユーザーフィードバック:
「今の目標はトップの真ん中に。その左右に矢印で月(期間)を切り替え。
そこから一段上に出ると、月ごとのボードがカードで並ぶ。ライトモードに。
Figmaのような水玉グリッドも。」

## 1. 盤の階層 — 2階建て

```
月の一覧(カード)   ← 一段上。年表。どの月が熱いかを一望する。
   ↕ ⊞ / Esc
月の板(キャンバス) ← 作業場。円と房、ドラッグ、記録。
```

トップ中央の1枚のカードが両方の階層の錨:
**現在のフォーカス → 目標名 → 残り日数・≈% →(区切り線)→ 期間名 + 内訳**。
期間名の行がそのまま一覧への入口(⊞)。左右の `‹ ›` が板送り。`← →` キーと `Esc` も同義。

## 2. 円がどの板に載るか(唯一の規則)

| 状態 | 載る板 |
| --- | --- |
| 期限あり・未来/今月 | その期限の月 |
| 期限あり・**未達成のまま超過** | **今月の「持ち越し」列**(過去に置き去りにしない) |
| 期限あり・達成済み・過去 | その月に残る(その月の成果) |
| 期限なし | 「期限未定」の板(末尾) |

円は必ずどれか1つの板にだけ在る(重複表示なし → 盤座標が競合しない)。
遅れは常に *いま* の問題なので、持ち越し列は今月の板の左端に critical 色で現れる。

## 3. 月の中の列 = 旬

`上旬(1〜10) / 中旬(11〜20) / 下旬(21〜末)` × ワークストリーム行。
持ち越しがある今月だけ、左端に `持ち越し` 列が増える(4列)。
期限未定の板は単一列。列見出しは `columnsFor()`、座標は `boardAutoLayout()`(純関数・テスト済み)。

## 4. 板をまたぐ移動 = 期限の変更

円の下の期限チップがそのまま移動口。日付を選ぶ / 「翌月末へ →」 / 「期限を外す」。
変更すると円はその月の板へ移り、トーストの「その板を開く」で追いかけられる
(`aiment:goto-period` カスタムイベント)。
新規作成ダイアログの期限は**開いている板の月末**が既定 — 置いた円がその板から消えないため。

## 5. 一覧カード = 本物の縮小図

カードの中身はその月の実配置の縮小(`effectivePositions`)。円の相対位置は本物、
直径だけカード間で揃える(14〜30px、重み比例)。塗りは進捗の扇。
上辺3pxの色 = その月の最大切迫度。今月のカードだけ primary のリング。
主役1行(`3/5 VTuber候補5人がDMに返信`)+ 内訳(円N・残タスクN・持ち越しN)。
空の月も「この月に置きにいく →」として並ぶ(前後1か月ぶんの余白を常に用意)。

## 6. 「白い作業台」= ライトモード

規則は G-redesign のまま(大きさ=重要度 / 色=切迫ランプ / 強調は危険だけ / 減光=停滞)。
白地では **明るい＝安全、暗く濃い＝切迫** に反転させ、輝度差で緩急をつくる:

| トークン | 暗(旧) | 白地(新) | 用途 |
| --- | --- | --- | --- |
| calm | #aecbfa | #5c72a6 | 期限が遠い |
| warm | #ffd54d | #a76a05 | <7日 |
| hot | #ff9838 | #c25008 | <3日 |
| critical | #ff5b5b | #d0342c | 当日・超過・持ち越し |
| achieved | #3ddc97 | #0b8a52 | 達成のみ |
| action | #4fd1ff | #0b6fd0 | アクションのみ |

グローは白地では効かないため、**リング(0 0 0 3px)+ 落ち影**に置換(`.glow-*` / `warn-pulse`)。
脈動は引き続き画面で1要素だけ(その板で最も古い超過円)。
地は `#eef0f4` の作業台に **22pxの水玉グリッド**(Figma)。盤面は React Flow の
`<Background variant="dots">` で盤と一緒にパン/ズームし、一覧とカード内は静的な水玉(`.dot-canvas` / `.mini-canvas`)。
円はマットな白 + 2pxのランプ縁 + 1枚ぶんの影 — 紙の駒を作業台に置いた感触。

## 7. E2Eで見つけた本物のバグ(2件目)

**Reactのポータルはツリーを辿ってイベントが伝播する。**
実(ベリー)のポップオーバー内のクリックが円の `onNodeClick` に届き、
タスクを完了するたびに房が閉じて localStorage の展開状態まで消えていた。
→ ノード内で使う `PopoverContent` は `onClick={stopPropagation}` で必ず止める。
(1件目は「フルカバーのオーバーレイが `onNodeClick` を飲む」— 追補Iを参照。)

## 実装のときに踏んだ落とし穴

1. **`setPointerCapture` は click を殺す。** 積み木のドラッグ開始時に紙側で
   ポインタを捕獲すると、`pointerup` の宛先が紙に変わり、タイトルなど中のボタンの
   `click` が発火しなくなる。紙は画面全体なので捕獲は不要 — バブリングで足りる。
2. **タイトルは「掴む」対象でもある。** `onPointerDown` で `stopPropagation` すると
   タイトルを掴んで動かせない。押した座標を覚えておき、**4px未満なら編集・以上なら
   ドラッグ**と後から判定する(`wasClick`)。
3. **ホバーで出るボタンは幅を食い続ける。** `opacity-0` のままレイアウトに残るので、
   積み木の幅がタイトルより常に広くなる。画像もそうなっているのでこれは正しい。
4. **`0/1` の分数はノイズ。** 進捗の分数は `done_subtasks > 0` のときだけ出す。

## 追補III-b — やり直しとカメラ (2026-09-07)

### やり直し (`⌘Z` / `⇧⌘Z`)

- 山札の出し入れは `src/lib/history.ts`(純粋関数・14テスト)、Reactへの接続は
  `src/components/board/history.tsx`。操作のたびに `{label, undo, redo}` を1組記録する
- **DBのスナップショットは取らない**。逆操作をサーバーアクションで投げ直すだけなので、
  2人で同時に触っても相手の変更を巻き戻さない
- 作成のやり直しは「redoすると新しいIDになる」ので、クロージャの `id` を毎回書き換える

**落とし穴(実際に踏んだ):** `setState` の更新関数の中で `entry.redo()` を呼ぶと、
React の開発モードが更新関数を2回実行するため**積み木が2個できる**。
副作用は更新関数の外に出し、山札は ref、ボタンの活性だけ state に写す。

### カメラ

- `pan` と `scale` を **1つの `cam` state** にまとめた。ホイール拡大は「今の倍率」を
  必要とするので、別々の state だと古い値を掴んで拡大の中心がずれる
- ホイールは **React の `onWheel` ではなく素の `addEventListener(..., {passive:false})`**。
  React の `onWheel` は passive なので `preventDefault()` が効かず、
  ⌘+ホイールがブラウザのページ拡大に持っていかれる(これが「ズームするとページ自体が拡大する」の原因)
- 水玉は紙の模様として扱う: 固定要素の `background-position` をカメラの平行移動、
  `background-size` を `DOT_GAP * scale` にする。画面に貼りついたままだと
  「紙を動かしても模様だけ付いてくる」= カメラに合わせて動いて見える

## 追補III-c — 積み木を積む (2026-09-07)

### 形

木構造。各積み木は「自分の下にある土台」(`milestones.parent_id`)を1つ持つだけ。

```
   [ A ] [ B ]      同じ段(= 同じ parent、sort_order で左右の順)
   [    C    ]      C は上の段を支える幅まで伸びる
```

**座標を持つのは `parent_id === null` の積み木だけ。** 上に載った積み木の位置は
土台の座標と親子関係から毎回計算する(`src/lib/stack-layout.ts`、23テスト)。
これで「塔ごと動く」「幅の辻褄が合う」が自動的に成立し、保存する数字も減る。

- `subtreeWidth(n) = max(自分の幅, 上の段の合計幅)` — 土台が伸びるのはこれ1行
- 段の中の子は**下ぞろえ**。サブタスクを開いた子は上へ伸びるので、土台に重ならない
- `findDrop` は掴んでいる積み木の**頭の中心**で判定: 上半分=載せる / 下半分=下に敷く /
  左右25%=横に割り込む(相手に土台がある時だけ)
- 点線ガイドは「その移動を当てはめた木」をもう一度 `layoutAll` に通して出す。
  推測で描かないので、離した位置と必ず一致する

migration: `drizzle/0003_loud_moondragon.sql` (`milestones.parent_id`)

### 落とし穴

- **明示幅で描く必要がある。** 積み方の計算に幅が要るので、面の幅は CSS の自動伸縮ではなく
  `blockWidth(title)` の値を渡す。ずれると土台の伸びが合わなくなるので、
  この関数は「持ち手28 + 余白18 + 担当者26 + 隙間×4 + 文字 + ホバーボタン46」で実測に合わせてある
- **E2Eは積み上げを最初にやる。** 後半の手順は盤を書き換えるので、
  seed直後の配置を前提にした判定は先に済ませる(順序を変えたら6件落ちた)

## 追補III-d — 積み方と掴み心地の調整 (2026-09-07)

作者からの指摘4件。いずれも III-c で入れた挙動の上書き。

| 指摘 | 直したこと |
|---|---|
| 上に行くほど積み木が小さくなる | **幅は `blockWidth(title)` だけで決まる**。土台は上の段を支えるために伸びない(`subtreeWidth` を廃止) |
| 重ねたら左ぞろえに | 段の中は中央ぞろえ → **左ぞろえ**(`place()` の `cx = left`) |
| ぴったりくっつけたい | `STACK_GAP_X` / `STACK_GAP_Y` を **0** に。上の積み木の厚みの影が下の積み木の天面に落ち、それが継ぎ目に見える |
| 掴むと影が伸びる | `.brick-lift`(`--depth-y` を12pxに伸ばす)を廃止。**`.brick-raised`** = 塔ぜんぶを `translateY(-7px)`、**`.brick-lifted`** = 掴んだ本人にだけ `filter: drop-shadow(...)`。`drop-shadow` は box-shadow を含む実際の形に落ちるので、持ち手と面がひとつの塊として浮く |
| 掴んでいる間、上の積み木も動かしたい | ドラッグ開始時に `isDescendant` で塔の全IDを集め、掴んだ積み木のズレ(`dragShift`)を全員に足して描く |

**残っている癖:** 段の中の子は**下ぞろえ**(body+枝の下端をそろえる)。
だから、たたんでいる積み木は土台にぴったり載り、サブタスクを開いた積み木だけが
枝のぶん上へ持ち上がる。これは「枝が土台に重ならない」ための唯一の配置で、
上ぞろえにすると畳んでいる兄弟が宙に浮く。塔が上に伸びて期間ピルの裏に入ることはあるので、
そのときは紙をパンする。

## 追補III-e — 描画順・横並び・重要の旗 (2026-09-07)

| 指摘 | 直したこと |
|---|---|
| たまに描画順がおかしい | `Placed` に **`depth`(地面から何段目か)** を持たせ、`z-index = 10 + depth*2` と DOM の並び順の両方をそれで決める。以前は全部 `z-index:10` で、配列の順(作った順)がそのまま前後になっていたため、下の積み木が上の積み木の厚みを塗りつぶすことがあった |

## 追補III-f — 描画順の反転・IME・取り組み中・期限UI (2026-09-07)

### 描画順は「上の段ほど奥」

III-e で「上の段ほど手前」にしたが逆だった。**下の積み木が手前に来て上の積み木の下端を隠す**
ことで、奥から手前へ積み上がって見える。手前に来ると平らに見えてしまう。
`zIndex = (dragging ? 200 : 40) - depth * 2`、DOM の並びも depth の**降順**。

### 日本語変換中の Enter

かな漢字変換の「変換を確定する Enter」と「入力を決定する Enter」は同じキーなので、
変換の途中で入力欄が閉じていた。`isComposing()`(`src/lib/utils.ts`)で弾く
— `nativeEvent.isComposing` に加え、保険で `keyCode === 229` も見る。

## 追補III-h — 取り組み中の輪の仕上げ (2026-09-07)

- **輪は「厚み(影)まで含めた高さ」に合わせる。** 面だけ(52px)で測ると輪が上にずれて見えるので、
  `BLOCK_H + BLOCK_DEPTH`(=57px)を囲う。上下の余白が同じか実測して確認する
- **中は薄くその人の色**(`color-mix(... 11%, transparent)`)。塗るのは**いちばん外の輪だけ**で、
  色は最初に取り組みはじめた人のもの。人数ぶん重ねると濃さが変わり、
  面の色(桃=重要)が塗りつぶされてしまう
- **点線はゆっくり流れる。** CSS の `border-dashed` は動かせないので、SVG の `rect` に
  `stroke-dasharray: 9 7` + `stroke-dashoffset` のアニメーション(`.ants`、3秒/32px)。
  32 = 16px周期 × 2 なので継ぎ目が出ない。`prefers-reduced-motion` で止まる。
  動くのは取り組み中の積み木だけなので、コストは盤の大きさではなく「取り組み中の数」に比例する

## 追補III-i — 幅の決まりを2つに、塗りは奥へ (2026-09-07)

| 指摘 | 直したこと |
|---|---|
| 薄い色はタスクの奥に | 印の層を**2枚**に分けた。**塗り**は積み木より奥(z-index 2)、**点線・名札・選択枠**は手前(z-index 150)。塗りが手前だと面の色(桃=重要)が濁り、点線が奥だと隣の積み木に隠れて欠ける |
| 短いタスクは短い箱に | `blockWidth` の下限 240 → **150**、内訳も実測に合わせて `98 + 文字`。`MIN_FACE_W` 212 → 84。分数チップ(`2/5`)も `blockExtrasWidth` に数えるようにした |
| 複数つながったら土台は伸びる | III-c で消した `subtreeWidth` を**復活**。`max(名前ぶんの幅, 上の段の合計幅)`。ただし**そろえ方は左のまま**(III-d で中央→左にした判断は維持) |

**幅の決まりは最終的にこの2つだけ:**

1. 基本は名前の長さ
2. 上の段を支えきれないときだけ、土台として伸びる

III-d では「伸ばすと上に行くほど小さく見える」として伸縮そのものを捨てたが、
実際の原因は**中央ぞろえ**のほうだった。左ぞろえのまま伸ばせば、
土台に見えて、かつ上の段が小さく見えることもない。

積み木の `z-index` は `Math.max(6, ...)` で下限を切る — 段が深くても塗りの層(2)より下に行かせない。

## 追補III-j — 被っている所だけ点線を薄く (2026-09-07)

輪は積み木より外へ出るので、隣や上に載った積み木を横切る。全部くっきり描くと
線が交差して読めなくなるため、**被っている所だけ薄く**する。

やり方は SVG のマスク。1つの輪につき `rect.ants` を2本描く:

1. 全周を `opacity 0.28` で(被っている所はこれだけが残る)
2. 同じ輪を `mask` つきで — マスクは「白=全面」から「被っている積み木の矩形を黒で抜いた」もの

`coversOf()` が、その輪の座標系に直した「被っている矩形」を返す(交差判定つき)。
2本とも同じ `.ants` を持つので、破線の位置がずれない。

**注意:** マスクの矩形はドラッグ中の位置(`dragShift`)も見る必要がある。
`coversOf` は `dragShift` を参照するので、宣言順が後になる — 前に置くと
「宣言前に使っている」で lint に落ちる。
